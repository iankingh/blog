規格卡住時，我想先分辨：現在缺的是一個能問清楚的答案，還是一個必須操作過才能判斷的答案？前者適合繼續對話，後者可以用小型原型，把抽象的需求變成可比較的選項。

這是我閱讀 Matt Pocock 的 `/prototype` 示範後整理的判斷方法。影片中的搜尋案例屬於 Matt 的實作；本文的整理與練習提案，不代表我已在自己的專案完成同樣的成果。

<!--more-->

適用：已經知道大致功能範圍，卻仍難以決定介面、互動或狀態行為的開發工作。本文整理來源影片的方法與設計選擇，不提供某個版本的技能安裝教學，也不把影片中的 token 用量視為通用成本。

## 先把不確定的問題寫出來

「做一個好用的搜尋」很難驗收。「使用者是在找一張圖，還是找某一次保存的快照？」就能引出具體設計。

Matt 在影片中將原型描述為用來回答問題的拋棄式程式碼。他的重點是讓規劃過程包含試用與回饋，而不是期待一份更長的文字規格直接消除所有不確定性。[回看 0:59](https://www.youtube.com/watch?v=n0VhIVtviC0&t=59s)

我會把待決問題改寫成下面這樣：

| 還不夠具體的需求 | 可以拿去探索的問題 |
| --- | --- |
| 搜尋結果要清楚 | 依圖分組，還是把符合條件的快照直接平鋪？ |
| 操作不要太複雜 | 改變搜尋字詞時，篩選條件應保留還是重設？ |
| 資料狀態要正確 | 目前版本和歷史快照重複出現時，應如何辨識與去重？ |

這張表是我的整理，不是影片提供的標準需求模板。它的用途是縮小原型範圍，讓試作結束時能回答原本的問題。

## 什麼時候值得做原型？

Matt 的判準很直接：當自己開始想親眼看、親手操作，光靠文字就可能不夠。[回看 2:37](https://www.youtube.com/watch?v=n0VhIVtviC0&t=157s)

我將它整理為三種情況：

- **規則已明確**：例如確認視窗需要取消與確認，先把規則說清楚即可。
- **呈現或操作仍不確定**：做能切換不同方案的 UI 原型，用相同資料比較。
- **狀態模型難以推演**：考慮小型互動式終端程式，逐步探索事件順序。

最後一項來自影片後段的用途介紹；影片沒有展示完整的後端狀態機實作，因此不能把它當成已驗證的後端教學。[回看 8:53](https://www.youtube.com/watch?v=n0VhIVtviC0&t=533s)

原型也有成本。Matt 提到，文字討論會少花 token，但產物較不具體。我的理解是：是否試作，應由待決問題決定；不需要把每個小問題都做成展示頁。

## A、B、C 比較後，為什麼還需要 D？

影片的應用程式同時保存 diagram 與 snapshot，搜尋設計必須處理不同層級的結果。Matt 沒有直接選一個初版，而是透過操作提出新的組合。[案例起點 3:57](https://www.youtube.com/watch?v=n0VhIVtviC0&t=237s)

| 版本 | 可以觀察到什麼 | 後續決策 |
| --- | --- | --- |
| A | 搜尋框位於右上方，快照依 diagram 分組。 | Matt 喜歡搜尋框位置，不喜歡分組。 |
| B | 左側清單與右側卡片形成主從面板。 | 試查改變字詞後的篩選重設，並提出呈現上的不滿。 |
| C | 搜尋結果平鋪，仍有 Both／Name／Content 範圍切換。 | 喜歡版面，但部分標示太技術化，也有目前版本與快照的呈現問題。 |
| D | 結合 A 的搜尋框與 C 的版面，進一步去重並移除切換。 | Matt 確認重複結果消失，點開結果也能運作。 |

這裡最值得帶走的，不是 D 的畫面，而是形成 D 的理由。C 沒有分組側欄，不代表它完全沒有篩選；D 才進一步移除搜尋範圍切換。這個差別提醒我，試用紀錄要描述實際行為，不能只留下「喜歡 C」這種感受。[回看 D 版 7:33](https://www.youtube.com/watch?v=n0VhIVtviC0&t=453s)

## 試用之後，留下什麼才方便實作？

我的整理是把回饋寫成四件事：

1. **要解決的問題**：這輪原型究竟在確認什麼？
2. **選擇與理由**：保留哪個行為，排除哪個方案，原因是什麼？
3. **可操作的參考**：原型如何打開，使用哪組資料，怎麼重現差異？
4. **仍需正式驗收的部分**：哪些功能、測試與原型碼清理尚未完成？

影片中，Matt 預計將規格、設計決策與原型交給後續代理，完成正式整合並刪除原型程式碼。但影片沒有展示這些後續工作的完成結果。[回看 8:00](https://www.youtube.com/watch?v=n0VhIVtviC0&t=480s)

因此，原型中一次順利的操作，可以支持某個設計選擇，仍不足以證明整個正式功能已通過測試。

## 我會怎麼練習這套方法

以下是尚未執行的練習提案，並非自己的實測成果：

- 選一個既有清單頁，只處理「搜尋結果如何排列」這個問題。
- 用相同測試資料做兩種呈現，逐項記錄找資料時的差異。
- 決定保留的互動，寫下排除其他方案的理由。
- 正式整合後，另驗證選定行為、邊界資料與原型切換器的移除。

若只剩文案或明確規則需要確認，我會先繼續問答；若不確定性來自看與操作，就用原型增加可以討論的證據。這是我從案例得到的判斷原則，還需要在自己的工作中累積實際紀錄。

## 使用這個案例時的限制

- 影片是個人工作法示範，沒有跨專案的成效比較。
- Matt 自述前面一輪約用了十萬 token；這是單次工作的描述，不能當作所有原型的固定成本或換算價格。
